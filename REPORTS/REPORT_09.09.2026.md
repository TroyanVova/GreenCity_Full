Results
What I did:
Took the AWS base from the last period (VPC, Security Groups, ECR, IAM role) and turned it into a running cluster: started the `k3s` server and two agents, joined them into one cluster, and set up an ALB with path-based routing to three backend services.
Built a full Jenkins CI/CD pipeline for the AWS track, separate from the existing Proxmox pipeline: build and push three Docker images to ECR, deploy to `k3s` with `kubectl`, and check health at the end.
Set up Kubernetes RBAC for the pipeline's service account from nothing, adding only the permissions that real deploy attempts showed were missing.
Fixed a long chain of app-level startup bugs in `backcore`/`backuser` — wrong datasource env-var names, wrong probe timing, two more missing property placeholders — always fixing it through Kubernetes manifests or Jenkins credentials, never through the properties file shared with the Proxmox deployment.
Found and fixed a real infrastructure design problem: the ALB's path-based routing (`/core/*`, `/user/*`) assumed path rewriting that AWS ALB does not actually do. This silently broke the health checks, and would have broken every real API call from the frontend if it had not been caught.
Found and fixed a frontend build problem: the environment-variable substitution step the original project uses (`setenv.ts`) does not exist in this AWS-track fork's Docker build, so the built JS file shipped with literal, unresolved placeholders.
Caught a `.gitignore` bug that would have pushed the cluster's SSH private key and admin kubeconfig to the remote repository, before either file actually left the local machine.
What I achieved:
The site is publicly reachable end to end at `http://greencity-alb-1035474643.us-east-1.elb.amazonaws.com/` — frontend, backcore, and backuser all pass their health checks, and the Jenkins pipeline finishes with `SUCCESS`.
`backcore` and `backuser` both start reliably against the real RDS database, run their full Liquibase migration (443 changesets), and stay up with the new `startupProbe`/`readinessProbe`/`livenessProbe` setup.
The AWS deployment now has working, minimum-privilege Jenkins RBAC, a working way to pull images from ECR on self-managed `k3s`, and no secrets exposed in Git.
The path-routing mismatch between the ALB and the Spring Boot apps is fixed and written down, and the frontend's runtime configuration is now substituted correctly when the container starts.

Tools and Technologies Used
Terraform (AWS provider): EC2, Elastic IP, Security Groups, ALB (target groups + listener rules), RDS, ECR, IAM, `aws_ssm_parameter` data source, `-replace` to recreate one resource.
k3s (self-managed Kubernetes on EC2, not EKS): server/agent join through an SSM Parameter Store token, built-in containerd, no automatic way to connect to ECR.

Jenkins: declarative Pipeline, `withCredentials`, Secret-text credentials, agent tools (`aws` CLI, `kubectl`).
Spring Boot: relaxed environment-variable binding, Liquibase autoconfiguration, Hibernate `ddl-auto=validate`, `server.servlet.context-path`, Spring Security `permitAll` request matchers.
Angular / Docker / nginx: multi-stage Docker build, runtime configuration with `envsubst` in a custom `docker-entrypoint.sh`.
AWS ALB: path-based listener rules, and the fact that it does not rewrite paths.
Git: how `.gitignore` paths are relative, `git rm --cached`, checking history with `git log --all`.

Comments and Conclusions
This period followed the same pattern as the last report: problems only became visible the first time something really ran, end to end. The datasource env-var mismatch, the probes that were too short, the two missing property placeholders, and the ALB/context-path mismatch were all invisible on paper — every file looked fine on its own — and only showed up one at a time, as each earlier blocker was fixed and the pipeline got one step further. This is why the work stayed step by step: fix the crash currently visible in the logs, redeploy, then read the next error. A second lesson was the value of checking the real code instead of guessing. Reading `AzureCloudStorageService`, `EmailServiceImpl`, and `SecurityConfig` directly, instead of assuming what a stack trace or an HTTP status meant, turned a vague "startup probe timeout" into the right, small fix each time, and is also how we confirmed that `GOOGLE_CLIENT_ID` could safely wait, instead of being chased as another blocker. A third theme, carried over from last period, was keeping the two deployment tracks fully separate: every app-level fix went into Kubernetes manifests or Jenkins credentials, never into the `application-docker.properties` file the Proxmox deployment also uses — even when that meant a slightly longer fix, like setting `ADDRESS`/`GREENCITY_SERVER_ADDRESS` through an env var instead of editing the property directly. Finally, catching the `.gitignore` bug before the SSH key and kubeconfig left the machine was a reminder that a nested `.gitignore`'s patterns are relative to its own folder, not the root of the repository — a small detail that would have been expensive to fix later. By the end of the period, the AWS track reached the same point as a working deployment: a public URL, passing health checks, and a green pipeline — the same result the Proxmox track reached earlier in the project, but on separate infrastructure.
