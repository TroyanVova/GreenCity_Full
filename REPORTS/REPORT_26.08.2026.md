Goals
Main goal: Build a full auto-deploy pipeline for staging, separate from the on-demand job. The build now happens on `jenkins-agent`, not on the target VM. Images go to our own registry. The target VM only pulls and starts them. Every deploy is registered in the shared monitoring system automatically.
Other goals:
Set up one monitoring VM (Prometheus + Loki + Grafana) that collects metrics and logs from all environments, and test it on a real staging run.
Stop sending the GitHub Personal Access Token in plain text during checkout. Use an SSH deploy key instead.
Make the job start right away after a push, without opening any router ports. Use `smee.io` for this.

Results
What I did:
Built a new job, `GreenCity-Staging-AutoDeploy`, separate from the on-demand job, that always deploys to the same staging VM when someone pushes to a specific branch.
Moved the Docker image build from the target VM to `jenkins-agent`, using our own `registry:2` in between. Target VMs no longer need a heavy Maven/Angular build.
Set up a separate monitoring VM with Prometheus, Loki, and Grafana. It collects metrics and logs from all environments through file-based service discovery, which Jenkins updates after every deploy.
Replaced the GitHub Personal Access Token in the checkout URL with an SSH deploy key, for  `GreenCity-Staging-AutoDeploy`.
Set up an instant GitHub webhook using `smee.io` instead of Poll SCM, including a systemd service for the client on `jenkins-master`.
What I achieved:
Prometheus `/targets` shows three working jobs (`greencity-app`, `node-exporter`, `cadvisor`) with status `UP` for `env="staging"`.
Grafana dashboards (Node Exporter Full — `1860`, cAdvisor exporter — `14282`, Spring Boot/Micrometer — `12900`) show real data from the live staging environment.
Container logs (`core`/`user`/`frontend`) are visible in Grafana → Explore → Loki.
A push to branch `jenkins` starts `GreenCity-Staging-AutoDeploy` in seconds through the webhook, with no router ports opened.
Checkout now fully uses SSH — the PAT is no longer part of any URL and never appears in any `.git/config` file.

Prometheus, Grafana, Loki, node-exporter, cAdvisor, Promtail: central collection of metrics and logs from all environments through one monitoring VM.

ufw: firewall rules for the new monitoring ports on target VMs.

Comments and Conclusions
Just like in the last round of work, most of the real problems were not about the overall design. They came from small mismatches between how things are supposed to work and how they actually work: a missing firewall rule for a new port, an old community dashboard, a Node.js version that did not match a new package, and a broken system file caused by pasting text into an editor. None of the eight problems listed above could have been predicted in advance - all of them only showed up by running things against the real staging environment, step by step.
One case is worth a special note: the host-key verification problem. The first, obvious fix (add GitHub's key to `known_hosts` on one agent) did not work in practice, because the Jenkins agent - started over SSH from the controller — runs git commands in an environment where `$HOME` is not always what you expect. This fits a general lesson from this project: check your fix against a clear, independent signal (here, the "Never used" status on the GitHub deploy key), instead of stopping at the first explanation that sounds right.
Moving to SSH checkout and a webhook through `smee.io` finishes two items that were already planned in the last report ("move away from PAT-in-URL", "webhook instead of Poll SCM") — both are now done for the staging pipeline.
