Results
What I did:
Compared three ways to deploy on AWS (`k3s` on EC2, `EKS`, `ECS` Fargate), estimated the cost of each, and chose `k3s` on EC2 as the cheapest option that also uses Kubernetes.
Ran a decision session for three new workstreams (registry VM, Discord alerts, SonarCloud) and then built all three on the real infrastructure.
Moved the Docker registry from `jenkins-agent` to its own dedicated VM, and updated `insecure-registries` on every host that pushes to it or pulls from it.
Built five Grafana alert rules with the correct Query -> Reduce -> Threshold structure, connected them to Discord, and added a separate Discord notification for CI/CD failures from the Jenkinsfile.
Added SonarCloud static analysis as an early stage in the Jenkins pipeline for both backend Maven projects, running from each parent `pom.xml` so that module dependencies (`dao`, `service-api`) resolve correctly.
Found and fixed a batch of old, unnoticed `formatter-maven-plugin` errors in `backcore`/`backuser` test code - this was the first time the full Maven build ran in an automated pipeline.
Removed the Maven `target/` build output from Git, which had been causing file-ownership conflicts between local `mvn` runs and Jenkins' own checkout.
Spent a full day building the base AWS network and access layer: VPC, public subnets, Internet Gateway, Security Groups, ECR repositories, and an IAM role for EC2.
What I achieved:
Discord alert messages now show real values (`Value:`/`Description:` fields are filled in) instead of `[no value]`, for both firing and resolved alerts.
A real RAM-stress test triggered the `NodeMemoryHighUtilization` alert end-to-end, through Prometheus -> Grafana -> Discord, so the whole alert chain works.
The Jenkins pipeline now builds the full `backcore` and `backuser` Maven projects (this never ran as a full build in CI before) and runs SonarCloud on both.
`jenkins-agent` can push to, and target VMs can pull from, the new dedicated registry VM, with no HTTPS/insecure-registry errors.
The AWS account now has a working VPC, subnets, routing, security groups, ECR repositories, and an IAM role - ready for the next step, launching the EC2 instance.

Comments and Conclusions
This period's work had a few repeating patterns worth noting. First, several problems only showed up the first time something ran for real, end-to-end. The Maven build had never run as a full project before, which is why months of small formatting mistakes went unnoticed until now. The registry had never been pushed to from a separate host before, which is why the `insecure-registries` problem appeared right away. None of this was visible just by reading the configuration files - it only showed up when I ran the real pipeline. This is a good reason to test infrastructure changes live, not just trust them on paper. Second, the `node-exporter` firewall problem was a repeat of a mistake from an earlier report - a new VM needs the same `ufw` rules as every other one, and this time the fix was also added to the Docker build template, so future VMs come with the rule already in place instead of relying on memory each time. Third, quick manual fixes over SSH (running `mvn format` directly on `jenkins-agent`, or editing files as a different system user) kept leaving small problems behind - wrongly-owned `target/` files, an out-of-date local copy - that only showed up later as unrelated-looking errors. Moving that kind of fix back to a normal local Windows workflow with a plain `git push` removed the whole class of problem, not just one case of it. Finally, this period I also started planning the move to AWS. Comparing `k3s` on EC2, `EKS`, and `ECS` (Fargate) by cost and complexity, and choosing `k3s` on EC2, follows the same approach used for every other part of this project: pick the simplest and cheapest option that still teaches real, useful skills. The last day of the period was spent fully on this - building the VPC, subnets, Security Groups, ECR repositories, and the IAM role that the first EC2 instance will use.
